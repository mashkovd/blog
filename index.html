03 · Contract boundary

The proposal is the contract.

The implementer does not read the original issue. It works from the approved proposal.

IntentIssuewhat should change
→
ContractApproved proposalrequirements · design · tasks
→
ExecutionImplementerworks only from the contract

Why this constraint matters

If the proposal is incomplete, the agent should stop instead of silently reconstructing intent from hidden context.

Consequence

Acceptance criteria must be complete before approval — not discovered halfway through implementation.

04 · Control points

Two gates. Different owners.

HUMAN

Approve

Is this the right change? Is the proposal complete? Is the risk acceptable?

intent → durable approval signal

AUTOMATED

Review gate

Does the current PR head pass checks? Are blocking findings resolved? Is the evidence current?

head SHA + CI + reviews → gate result

Humans decide what should happen. Automation proves what is true now.

06 · Event-driven review

Fresh evidence beats agent memory.

A GitHub event wakes the workflow. The reviewer then re-reads the world as it exists now.

Invariant

07 · What to copy

You do not need MCTL to copy the pattern.

01Start with one loop

Choose one narrow path from intent to reviewed change.

02Make artifacts durable

Criteria, approvals and evidence must survive chat history.

03One owner per phase

Human, agent or automation — never two competing owners.

04Close the loop

Done means the platform observed the result, not merely that code merged.
